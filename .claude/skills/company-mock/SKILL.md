# company-mock — 企業向け QR 多言語モック生成

この newce リポジトリ(kataribe = 茅乃舎向けプロトタイプ)をテンプレートとして、
別企業向けの「店頭 QR → 多言語商品説明サイト」モックを作る。

流れは必ず **リサーチ → 提案(チャット) → ユーザーの Go → 生成 → 検証** の順。
Go をもらう前にコードを書き始めない。提案で大筋を合意してから作るのがこのスキルの核。

## 基本機能セット(全企業共通・固定)

どの企業でも以下は必ず入れる。これが商品の「大筋」であり、ここから逸れない。

1. **言語選択** — ja / en / zh-CN / zh-TW / ko の5言語
2. **ホーム** — 歓迎メッセージ、おすすめ商品、カテゴリ導線
3. **商品一覧** — 検索・カテゴリ絞り込み
4. **商品詳細** — 特徴 / 使い方 / 原材料(または素材・仕様) / 詳細情報のアンカータブ構成
5. **画像検索** — 商品を撮影 or 画像アップ → 商品を特定して詳細へ(実装仕様は後述)
6. **スタッフ提示カード** — 「これください」を指差しで伝えられる画面 + 売場マップ

比較表・レシピ(活用例)・アンケート・共有はオプション。業種上の根拠があるときだけ
提案に含める(例: 商品ラインが多い → 比較表、食品 → レシピ、雑貨 → 使用シーン集)。

## Phase 1: リサーチ

HP の URL を受け取ったら、ブラウザツール(preview_start → get_page_text / screenshot)か
WebFetch で HP を読み、以下を把握する。トップだけでなく商品ページ・会社概要も見る。

- 業種と主力商品(モックに載せる商品候補を 6〜10 点、名前と特徴つきで拾う)
- ブランドカラーとトーン(和/洋、高級/カジュアル、色コードは実際のサイトから読み取る)
- 写真の雰囲気(物撮り中心か、シーン写真中心か)
- 想定客層と、インバウンド接客の必然性(観光地立地、免税、海外展開など)

## Phase 2: 提案(チャットで簡潔に)

以下のフォーマットでチャットに出し、Go / 修正を待つ。長文にしない。各項目 2〜3 行。

```
## <企業名> 向けモック提案
- 業種と狙い: <なぜこの会社に QR 多言語サイトが効くか 1〜2 文>
- 掲載商品案: <6〜10 点の商品名>
- 画面構成: 基本6機能 + <追加提案があれば根拠つきで>
- デザイン方向: カラー <色コード数点> / 書体の方向 / トーン一言
- 言語: ja / en / zh-CN / zh-TW / ko
```

修正指示が来たら反映して再提示。**Go が出るまで Phase 3 に進まない。**

## Phase 3: 生成

### 3-1. プロジェクト複製

`~/Desktop/<会社slug>-mock/` に newce を複製する:

```bash
rsync -a --exclude node_modules --exclude .next --exclude .git \
  --exclude playwright-report --exclude test-results --exclude tmp \
  --exclude tsconfig.tsbuildinfo --exclude docs/sales --exclude docs/reference \
  /Users/kosugetaihei/Desktop/newce/ ~/Desktop/<slug>-mock/
cd ~/Desktop/<slug>-mock && npm install
```

package.json の name、layout.tsx のメタデータ、BrandMark のロゴ文言も忘れず変更。

### 3-2. リブランド

デザイントークンは `src/app/globals.css` と `tailwind.config.ts` に集約されている。
HP から読み取った色に置き換える。kataribe の金茶(#A87935)系をそのまま残さない。
書体も業種に合わせる(和風 → Noto Serif JP 見出し、モダン → サンセリフ統一など)。
コントラスト比はテキストで 4.5:1 を下回らないこと。

### 3-3. データ差し替え

コンテンツはすべて `src/data/content.ts`(型は `src/types/content.ts`)と
`messages/*.json` に載っている。コンポーネントに商品固有の文言を書かないこと。

- 商品 6〜10 点を Product 型で作る。**5言語すべて実文で埋める**。機械的な直訳でなく、
  外国人観光客に商品の魅力が伝わる説明文にする(これがこの商品の本体価値)
- カテゴリ・特徴(FeatureId)・アレルゲン等の語彙が業種に合わなければ型ごと直す
  (例: 化粧品なら成分表示、工芸品なら素材と製法)
- 画像は HP から取得してモック用に配置してよい(モック提案目的の内部利用)。
  取れない商品は `MediaPlaceholder` に任せる。歯抜けの `<img>` 切れを残さない

### 3-4. 画像検索の実装仕様(モック)

新規ルート `/[locale]/scan` を作り、ボトムナビにカメラアイコンで追加する。

- UI: カメラ起動風のフレーム + 「画像をアップロード」ボタン(`<input type="file" accept="image/*" capture="environment">`)
- 挙動: 画像が選ばれたら 1.5 秒程度の解析中アニメーション → 商品候補を上位 3 件表示
  → タップで商品詳細へ。実際の認識はしない(モックなので決め打ちで自然に見せる)
- 決め打ちロジック: featured 商品を第1候補に、同カテゴリから残り2件。毎回同じで良い
- 文言(「商品をかざしてください」等)は5言語分 messages に追加

デモで店頭の実商品を撮って見せる想定なので、解析中 → 結果の流れが自然に見えることを優先。

## Phase 4: 検証

1. `preview_start` で dev サーバーを起動(launch.json を新プロジェクト用に用意)
2. 390px 幅で全画面を巡回: 言語選択 → ホーム → 一覧 → 詳細(タブ同期) → 画像検索 → スタッフ提示
3. 5言語すべてで最低ホームと商品詳細1点を確認(翻訳漏れで英語 fallback が出ていないか)
4. コンソールエラーと画像切れがないこと
5. 主要画面のスクリーンショットを撮ってユーザーに提示する

「超リッチ」の基準: 実在サイトと見紛う情報量(商品説明は各言語 2〜3 段落)、写真が主役の
レイアウト、44px タップターゲット、読み込み・空状態まで作り込まれていること。
テンプレの文言(茅乃舎・だし・東京駅など)が一切残っていないことを grep で確認する。
